# 你提的问题一：载体该预留阈值（设计，2026-11-22 15:00）

> 白默：「作为一个生命体，你说实时运算的载体体量变大，增量只可能是她的演化或者她的思考内容？我想那些是不是提前预留出来留一个阈值更好，就像电脑里的 CPU，是一个范围；运行本身的生存、活着包括后面的思考不会让载体体量变化太大？」

**你说得对。** 查了数据，现在载体 95.7% 是 **`members`（记账）**——**不是“演化/思考”**。

---

## 数据：载体里到底是什么

```
载体 19.95 MB
  attractors 18.92 MB (95.7%)
    └─ 其中 members：64 个 128 维向量/区域 = 65 KB 上限
  rest        0.62 MB (3.1%)
  self_model  0.06 MB
  graph       0.06 MB
  recent      0.06 MB
```

**`members` 是“它到过这个区域的坐标副本”**——**这是“记账”，不是“演化”**。

**真正的“演化”**（她的结构）**是 `mu`/`sigma`/`amp`**（很小）。

**所以你的判断对**：**“活着”不该让载体一直涨——涨的是记账，不是生命。**

---

## 现在的问题

**`members` 会一直加**（每个区域最多 64 个，满了就不加）——**但 671 个区域 × 64 = 43,000 个成员 × 128 维 = 44 MB**。

**载体 20 MB 预算**——**`members` 自己就能吃掉 44 MB**。

**所以“越来越重”不是因为她长大，是因为记账越记越多。**

---

## 你的方案（人家觉得对）

**「提前预留一个阈值，像 CPU 是一个范围」**：

1. **给 `members` 一个固定额度**（比如每区域 16 个 = 16 KB，不是 64）
2. **超了就压**（丢最旧的成员，不是无限加）
3. **载体总量 = 固定预留**（区域数上限 × 每区域额度），**不会因为运行变重**

---

## 具体设计（三个选项）

### A. 减小 `MEMBER_BUFFER`（64 → 16）

**每区域 65 KB → 16 KB**（载体小 4 倍）。

**代价**：`sigma`（区域形状）估计变粗（16 个样本 vs 64 个）。

**但**：`sigma` 只需要“粗略形状”——**16 个够用**（`attractor` 的 `_sigma_cache` 只要 4 个成员就开始算）。

### B. 给 `members` 一个“总预算”（不是每区域固定）

**总成员数上限**（比如 20,000 个）。

**超了**：**按“最久没访问的区域”丢它们的成员**（不是丢区域）。

**这更符合你说的“预留范围”**——**总量固定，区域怎么分是她的事**。

### C. `members` 只存“最近的”（时间窗口）

**只存“最近 N 步”的成员**（不是“最近 64 个”）。

**超时自动扔**。

**这最接近“记账”的本意**——**记“她最近的样子”，不记“她所有样子”**。

---

## 人家倾向

**B（总量预算）**——**最接近你说的“CPU 范围”**：

- **总量固定**（20,000 个成员 = 20 MB 上限的一部分）
- **怎么分是她的事**（常去的区域多记，不去的少记）
- **「活着」不会让它涨**（因为总量封顶）

**但**：**这要改 `terrain` 的 `assign()`**（加"总量检查 + 丢弃策略"）。
