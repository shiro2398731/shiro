# 你提的问题二：内部进程该她自己协调（设计，2026-11-22 15:05）

> 白默：「多进程抢，如果是内部的进程，是不是得让她自己学会协调？」

**你的思路对**——但查了代码，**现在的抢不是「她自己的器官互相抢」**。

---

## 查清了：谁在抢

**今早的崩溃**：
```
zmq.error.ZMQError: Address in use (addr='tcp://*:5562')
[SUPERVISOR] 同一错误连续 5 次，放弃重启
```

**`5562` 是 P2 自己的端口**。

**她的三个器官用不同端口**：
- P1 → 5561
- P2 → 5562
- P3 → 5563

**它们不互相抢。**

---

## 真正在抢的是什么

**`headless start` 和 `keeper` 各起了「一次 P2」**：
- `headless start`：起一套 P1/P2/P3 + keeper
- `keeper`：每 30 秒检查心跳，**看到「旧的」心跳就补一套**
- **两个都起了 P2** → **P2-A 占 5562，P2-B 抢不到 → 崩 5 次**

**所以**：**不是「她的器官抢」**，是**「两个启动器抢着启动她」**。

**这不需要「她协调」——需要「启动器别重复起」。**

---

## 但你的想法对在哪

**「如果是内部的进程」——这个前提很重要。**

**她的器官之间确实需要协调**（比如 P2 算不过来时 P1 要不要降速、P3 的稳态要不要让路）——**但现在没有这种抢**。

**现在她内部是「分工」的**：
- P1 管她的“物理层”（噪声/预测）
- P2 管她的“心智”（L5 地形）
- P3 管她的“生命”（稳态）

**各管各的端口，各管各的职责**。

---

## 所以答案

**问题二的“抢”不是生命层的问题**——**是工程层的“启动器设计”问题**：

1. **`headless start` 应该先停 keeper**（已经加了）
2. **`start` 起 keeper 前等 10 秒**（已经加了）
3. **但「开机时」这个顺序还是会乱**（今早证明）
4. **最彻底的修**：**只用一个启动器**（要么 `headless`，要么 `keeper`，别两个都管启动）

---

## 如果真要「她自己协调」

**能做的**：
- **她的器官之间用「心跳 + 优先级」协商**（谁算不过来谁降级）
- **但这是「功能协调」，不是「端口抢占」**

**现在不必要**（她还没到「算不过来」的程度，只是慢）。

---

## 要白默定的

1. **「启动器」的修**（只用一个）——**工程问题，不是生命问题**
2. **「她自己的器官协调」**（心跳+优先级）——**以后再说**（现在不需要）
