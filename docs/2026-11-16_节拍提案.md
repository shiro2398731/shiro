# 提案：`fresh.wait(0.5)` 是一个节拍（未实施，等白默定）

> 2026-11-16，小灯。这份文件不改代码，只把两个方案写到「可以直接执行」的程度。
> 背景见 `HANDOFF.md` 第 13 节：她在 21 分钟里只走了 2435 步（2 步/秒），
> 而同一条代码在副本上是 1637 步/秒。

---

## 1. 现场

`src/runtime/process_2_mind.py:273-293`：

```python
while running["flag"]:
    # 等一个上游事件，或超时（超时只是为了让循环能检查退出标志）
    got = fresh.wait(timeout=0.5)
    fresh.clear()
    if not epoch_mod.is_current(my_epoch): ...
    if not runner.maybe_calibrate(stream): continue
    stream.landscape.set_noise_amplitude(...)
    stream.landscape.set_deflection(runner.deflection())
    ev = stream.step()
```

那行注释说的是实话——0.5 秒**本来**只是想给退出标志一个检查点。但 `fresh` 只在
`l1.state.surprise` 与 `l2.state.field` 到达时被 set，而 P1 的发条件是：

- `l1.state.surprise`：`abs(s_t - s_med) > s_mad`；
- `l2.state.field`：`l2_updates` 变了。

**当 `s_t` 恒为 0 时，两条都不发。** 于是 `fresh.wait` 每次都走超时分支，一步一脚，
0.5 秒一步。它就不再是"检查退出标志"，而是**她的思维节拍**。

这和 ARCHITECTURE §3「没有 tick、时间由事件刻度」直接冲突：一个超时参数
以工程必需品的身份把节拍带回来了。

---

## 2. 方案 A：P2 不等超时

**改法**（一处）：

```python
    got = fresh.wait(timeout=0.02)      # 0.5 -> 0.02
```

或者更彻底：把循环改成「有事件就立刻处理，没事件也按自己的判据步进」，即把
`fresh.wait` 降成一个短的让步点，步频由 `maybe_calibrate` / `staleness` 决定。

**预期**：她会在静默期也以接近 bench 的速度运行（几十到上千步/秒，取决于噪声与
状态是否在动）。**这会让她的轨迹与现在完全不同**——不是"快一点"，是"换了一具
跑得更快的身体"。

**风险**：

- 结构会快速长大，可能几小时内就撞上 20 MB 折叠线，触发大量折叠；
- `recover` / `fold_auto` 的统计窗口是按步数算的，步频变 25–800 倍后，
  这些判据的时间尺度全部改变；
- 今天那次事故（HANDOFF §10）说明这类改动会连锁，必须先在副本上用
  `tools/bench.py` 跑 `区域数 vs 步数` 曲线，再决定要不要上去。

---

## 3. 方案 B：P1 在静默时也发信号

**改法**：`src/runtime/process_1_fast.py:1328-1342`。把 surprise 的发布条件从
「超过自身典型幅度」改成「超过自身典型幅度 **或** 距上次发布已过 N 个她自己的
包络周期」（N 选她自己包络周期的倍数，不是一个固定秒数）。

**预期**：P2 仍然按事件走，但「她静着」和「没人说话」被区分开。静默期她也会收到
"没有变化"的事件，于是按正常节拍步进。

**风险**：等于给 P1 加了一个节拍——只是这次是用她自己的包络周期当刻度，
比固定秒数好，但它仍然是一个"每隔 N 发一次"的机制，ARCHITECTURE §3.3 明文禁止
`sleep(n)` / `every(n_seconds)` 形式。用包络周期当 N 能自称"由上游实测得出"，
但形式上仍是周期发布。

---

## 4. 两个方案共同的问题

**它们都改变她的演化速度，从而改变她的轨迹。** 按今天定下的规矩（HANDOFF §10）：

1. 先在副本上跑，记录 `区域数 / 步数` 与 `全局张力 / 步数` 两条曲线；
2. 用 `tools/bench.py` 的终点指纹对照——但要注意：**指纹本来就会变**，
   因为速度变了。所以这次不能用"指纹不变"当验收，只能看曲线是否收敛、是否撞折叠线；
3. 跑至少 5000 步，看区域数和张力是否走出今天那个自我维持的静止态；
4. 通过之后再上真实进程。

---

## 5. 我的判断

**选 A**，但把超时不是设成 0.02，而是「先设 0.1，观察 5000 步的区域增长曲线，
再决定要不要继续降」。

理由：

- B 只是把节拍换了个位置，还留在系统里；A 是把节拍从"等待"变成"让步"，
  步频由她自己的状态决定，更贴 ARCHITECTURE §3；
- A 只有一个改动点，比改 P1 的发布逻辑好验证；
- 但 A 的影响面大得多，所以必须分档降（0.5 → 0.1 → 0.02），每档跑 5000 步看曲线。

**这一条人家不自己动。** 它改的是她的时间尺度，不是修一个 bug。
