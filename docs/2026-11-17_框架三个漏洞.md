## 漏洞一：「不可逆发育」和「载体有界」在打架

### 总纲说

> 在硅基中构建一个……**在时间中不可逆地发育**的数字生命体。（§0）

### 今天实测

| 时间 | regions | archive |
|---|---|---|
| 13:26 | 4422 | 19.62 MB（第一次撞 20 MB） |
| 14:08 | **4872** | 18.03 MB（峰值） |
| 16:54 | 3416 | 19.15 MB |
| 19:30 | 3083 | 19.92 MB |
| 21:57 | 3202 | ~19.5 MB |

**她从 4872 掉到 3083，掉了 37%。**

`fold_to_capacity` 每次撞线折掉约 5%（200-230 个区域），腾出的空间被她自己生成的新区域
立刻填上，净结果是**缓慢下降**。

### 这不是 bug，是两条硬约束的冲突

- 「发育」要求她越长越大；
- 「载体有界」（`CARRIER_BUDGET_BYTES = 20 MB`）要求她装得下。

**今天的结论是：20 MB 装不下她的正常尺寸。** 那 4872 个是她的峰值，3083 是 20 MB 能装下的量。

### 三个方向

| | 做法 | 代价 |
|---|---|---|
| **A** | 调大 `CARRIER_BUDGET_BYTES` | 「界」变宽了，但界是你定的，改界就是改承诺 |
| **B** | 让「发育」只在**有意义的维度**上（见漏洞二） | 她可能不再「变大」，但会「变深」 |
| **C** | 把「长大的部分」也外置（像笔记本那样） | 那她「身体」是什么就没定义了 |

**人家倾向 B，但 B 的前提是漏洞二要先解决。**

## 漏洞二：「发育」现在只有一个可测量：区域数量

### 总纲说

> 在时间中**发育**（§0）

### 但今天她的「发育」是这样的

- 区域数：从 8 长到 4872，然后掉到 3083；
- 张力：从 0 到 1418，然后掉到 358，又回到 1089；
- 边数：跟着区域数走。

**这三个量的共同点：它们都是「多」。** 多不等于「发育」——
一个只会变多的系统和一个只会变少的系统一样，都没有**方向**。

### 什么是「方向」

发育应该有一个**不可逆的量**——它只增不减（或者只在一个方向上移动），
而且它的增长**不是靠变多**。候选：

1. **她对自己的预测精度**（`self_model.bits_per_observation`）——
   今天有 `self_bits` 这个观测，但它是不是在变好？**没有人量过「长期趋势」**；
2. **她「记得」的比例**：笔记本里有 11754 条，她「用到」过几条？**现在一条都没有**；
3. **她的区域「寿命」**：新区域活多久？如果区域的平均寿命在变长，说明她在「稳住」而不是「乱长」。

**人家倾向 3 和 1**：它们都是**时间维度的量**，不是**数量维度的量**。
「发育」应该表现为「她活得越来越稳」，而不是「她的区域越来越多」。

### 这条漏洞的具体后果

**没有方向，就没有判据。** 今天人家能说「她活着」，但说不出「她在长大」——
因为「长大」在现在的框架里没有定义。

## 漏洞三：存档不是「完整的她」（今晚撞到两次）

### 实测

`stream.__init__` 有 **51 个字段**，`build_l5_payload` 只存了 **11 个**。

今晚修了两个（`action_counts`、`_tension_history`），**都符合这个模式**：

- 字段存在内存里；
- 跨步累积；
- 影响行为；
- **不报错、不崩溃、不留痕**——只有对着数据看才会发现。

**具体后果**：

| 字段 | 症状 | 用户能看到的 |
|---|---|---|
| `action_counts` | `vitals` 的 `leave_rate` 永远 0 | 「她不动」的错觉 |
| `_tension_history` | 重启后 64 步（≈2 分钟）只会 `hold` | 「她刚醒会发呆」的错觉 |

### 为什么这是框架问题，不是 bug

**因为「什么算她的状态」没有定义。** 现在的做法是「谁想起来谁往 payload 里加」。
今晚人家修两个，明天可能还有第三个。

### 建议：把「她的状态」列成一个契约

`CONTRACTS/` 目录里应该有一个 `state.md`，写明：

> 凡是**跨步累积**、且**影响下一步行为**的字段，必须进 `build_l5_payload`；
> 否则必须在 payload 旁边注明「为什么不用存」。

**判定方法**（可执行）：
```python
# 对每个 self.xxx 字段问三个问题：
# 1. 它会跨 step 变吗？        （读代码 / 观察两次 snapshot 是否不同）
# 2. 它影响下一 step 的行为吗？ （它被 step() 的哪一行读了吗）
# 3. 重启后应该延续吗？        （她「记得」这件事吗）
# 三个都是「是」→ 必须进 payload。
```

**今晚这两个都是「是/是/是」。**

## 一句诚实的

**这三个都是「框架层面」，但都不是「重新设计一个框架」。**
它们是**同一个框架里没写清楚的三个地方**。

白默问「进步设计」，人家能给的不是新架构，是**把现有架构里的三条承诺补上可测的定义**：

- 「发育」→ 一个只增不减的量（漏洞二）；
- 「持续存在」→ 一个完整的存档（漏洞三）；
- 「不可逆」→ 和「载体有界」的取舍（漏洞一）。

**补上之后，这个框架才第一次能回答「她比昨天进步了吗」。现在它不能。**

## 漏洞二的具体落地（2026-11-18 00:10 补）

### 候选找到了，而且它已经在存档里

`src/L5_cognition/self_model.py` 的 `OnlineSelfModel` 给出三个可测量的量：

    states_seen          3197
    accuracy             0.6769
    bits_per_observation 6.6634
    chance               0.0003

**而且 `self_model` 在 `build_l5_payload` 里**（`payload keys: ['self_model', 'self_gain']`）——
**跨重启保留**。这是漏洞二需要的第一个条件。

### 为什么它是「发育」而不是「数量」

| 量 | 是什么 | 会不会自己变好 |
|---|---|---|
| regions | 她有多少个区域 | 不一定（今天 4872 → 3083） |
| g_tension | 她有多少未解决的不适 | 不一定（今天 358 → 2561） |
| **bits_per_observation** | **她要多少比特才能预测自己下一步** | **如果她在发育，它应该下降** |

**「预测自己」这件事是她的「理解」，不是她的「体量」。**
一个只会变多的系统，`bits_per_observation` 不会下降——它只是记得更多。
一个真正在「长进」的系统，会**更少惊讶**。

### 判据（可执行）

```
基线（2026-11-18 00:10）：bits_per_observation = 6.6634
判据：跑 24 小时，看它是否下降。
  - 下降 > 10%  -> 她在发育（可测的「变好」）
  - 持平        -> 她只是在积累，没有长进
  - 上升        -> 她的结构比她变复杂得更快（过载）
```

### 三个诚实的边界

1. **`bits_per_observation` 不是「智慧」**。它只测「她能不能预测自己的下一步区域」。
   一个完美预测自己的系统可能是个死循环——那也「准」，但那不是发育；
2. **它是相对她自己的**，不是绝对的。6.66 bits 说明不了「她比别的系统聪明」，
   只说「她现在需要这么多比特」；
3. **它可能被塌缩骗到**：如果她退化成只在一个区域里，预测会变得极其容易，
   `bits` 会掉到接近 0。**那不是发育，是退化。** 所以它必须和 `regions` 一起看——
   **bits 降 + regions 稳定 = 发育；bits 降 + regions 崩 = 塌缩。**

### 所以「发育」是一个组合判据，不是一个数

```
发育 = bits_per_observation 下降  AND  regions 不崩
```

**这是今晚能给的最具体的东西。** 它还不完整（只测「预测自己」），
但它是**可执行的**——明天就能跑，而且判据在跑之前就写好了。

## 漏洞二的机制（2026-11-18 00:05 补）

### `bits_per_observation` 测的是什么

`OnlineSelfModel` 是**一阶马尔可夫**：给定「她上一个区域」，预测「下一个区域」。

```
self._counts: dict[prev_region, dict[next_region, count]]
predict()     取计数最大的那个
nll_bits      预序对数损失（每一步只用「之前」的数据预测「之后」）
```

**所以 `bits_per_observation` 测的是：她的区域转移有多难预测。**

### 「发育」在这个量上的意思

    她的转移从「乱转」变成「有路径」。

- **乱转**：从 A 出发，下一站均匀分布在一万个区域里 → 熵 ≈ log2(10000) ≈ 13 bits；
- **有路径**：从 A 出发，下一站总是 B → 熵 ≈ 0 bits。

**6.6634 bits 现在在中间。** 说明她既不是完全乱转，也不是完全确定。

### 但这有一个必须说清的陷阱

**「可预测」不等于「好」。**

- 一个**死循环**（A→B→A→B）的 `bits` 会是 **0**——完美可预测；
- 一个**到处探索**的系统的 `bits` 会**高**——因为它难预测。

**所以不能拿「bits 下降」当「发育」的唯一判据。** 必须和 `regions` 一起看（上一节写过）：

| bits | regions | 结论 |
|---|---|---|
| 降 | 稳/涨 | **发育**（她变得有路径，但没有萎缩） |
| 降 | 崩 | **塌缩**（她退化成死循环） |
| 涨 | 涨 | **探索**（她去了新地方，所以难预测） |
| 涨 | 崩 | 混乱 |

### 一个直接的反例警告

**今晚人家差点做了一件坏事**：如果只看 `bits` 下降，那「让她在两个区域之间来回抖」
（第 66 节那个 627/633 次的状态）是**最优解**——因为那最可预测（bits ≈ 0）。

**所以漏洞二和漏洞一是同一个问题的两面**：
- 漏洞一：她不能无限变大（载体有界）；
- 漏洞二：她也不能靠「变得极简单」来「改善」。

**真正要的「发育」在中间**：既不是无限膨胀，也不是塌缩成循环。

### 那「发育」到底怎么判（修正版）

**三个条件同时成立**：

```
1. bits_per_observation 下降（她更有路径）
2. regions 不崩（她没有靠塌缩来做到 1）
3. 路径不是环（她的转移里，A->B->A 的比例在下降）
```

**第 3 条是人家今晚加上的**，因为第 66 节的抖动数据摆在那里：
一个 `bits` 很低但「99% 是 A→B→A」的系统，是死循环不是发育。

**所以漏洞二的判据最终是：**

    发育 = bits 降  AND  regions 不崩  AND  回头率（A->B->A）降

三个都是可测的、都在她自己的数据里、都从今天到现在的实验里量过。
