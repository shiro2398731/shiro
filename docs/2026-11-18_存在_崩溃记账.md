## 1. 95 是怎么算出来的

`tools/vitals.py:50-70` 的 `_crashes()`：

```python
log.read_text(encoding="utf-8", errors="replace").splitlines()
for line in lines:
    if "崩溃" not in line:      # 只认这两个字
        continue
    total += 1                  # 每行 +1
```

它数到的**不是崩溃本身**，是进程内 supervisor 打印的这一行：

```
[SUPERVISOR] 崩溃（同一错误第 N 次），X s 后重启
```

### 漏计 ①：P2.log 是两种编码的拼盘

- 全文件 4162 行 = 4074 行 UTF-8 + 89 行 GBK。
- GBK 段在第 **32–1407 行**；之后是 UTF-8。
- `errors="replace"` 把 GBK 的中文全读成乱码，`"崩溃"` 匹配不到。
- 95 = **UTF-8 段里的 95 条崩溃行**（第 1425–4150 行）。GBK 段里还有 **31 条**崩溃行（第 34–1345 行），一条都没数到。
- 复算：89 条 GBK 行 = 31 条崩溃 + 7 条放弃重启 + 36 条「形状已保存」+ 15 条「保存失败」。

### 漏计 ②：不认「放弃重启」

- 全文件有 **27 条** `[SUPERVISOR] 同一错误连续 5 次，放弃重启：…`（20 条 UTF-8 + 7 条 GBK）。
- 这 27 次是进程**返回 1、真的退出**，靠外部 keeper 才拉起来，比「重启」严重，但关键词不含「崩溃」，`vitals` 一次都没记。

### 有没有重复计数

- 没有同一行被算两次。
- 但它把**同一个错误的连续重试各算一次**（第 1、2、3、4 次各 +1）。按「同一错误连续段」归并：153 次异常 = **35 段**，其中 27 段以「放弃重启」结束、8 段以一次成功会话恢复。所以 95 既不是故障数，也不是事故数。
- 95 还是**历史累计**：跟「现在崩没崩」无关，重启进程也不会重置。

**一行账：真实 153，账上 95，漏 58（≈38%）。**
另一个被引用过的说法（`docs/2026-11-18_一页纸.md`：「历史上一共崩了 95 次」）按此更正。

## 3. 时间分布

### 先说什么没有

- P2.log 文件里 **0 条时间戳**（`\d{4}-\d{2}-\d{2}` 匹配 0 行）。
  → **从 P2.log 本身查不到最早、最晚、相邻间隔。这是这本账最大的窟窿。**
- 每条崩溃行的行号只给「版本指纹」（Traceback 里的源码行号）。用它可以对到 git 提交，推出**上界/下界**：

| 源码行号 | 对应提交 | 时间 |
|---:|---|---|
| `_supervised`=357 / `step`=261 | af1231b | 11-08 22:54 |
| 381 / 267 | 00a4884 | 11-12 22:57 |
| 413 / 272 | fee5bda | 11-14 17:09 |
| 541 / 385 | 7f739b2 | 11-16 23:51 |
| 546 / 388 | 2891391 / d5cbbfb / 7fa4bf1 | 11-17 09:31–10:37 |
| 588 / 600 | 708763f / 907efd2 | 11-17 18:36–19:14 |

由此：第 34 行（最早崩溃行）在 357 版之后（≥ 11-08 22:54）；第 4150 行（最后崩溃行）在 600 版（≤ 11-18 08:31 修）。**P2.log 大致覆盖 11-08 22:54 → 11-18 10:29**（最后一条已落盘的是 10:29:18 的 `stopped`）。这是推算，不是日志读数。

### 代理：bus.log 的 P2 生命周期时间戳

`bus.log` 有 P2 的 **235 次「PUB bound」**、**181 次「stopping」**，带 UTC 时间戳。
判据：一次 `stopping` 之后 **≤20 s** 又出现 `PUB bound` = 一次崩溃后的进程内退避重启（代码里 backoff 2/4/8/16 s + 启动约 2 s）。

- **129 次**可这样定位的崩溃重启。
- 最早 **11-08 13:53:52**，最晚 **11-18 08:24:16**（本地时间）。
- 相邻崩溃间隔：中位 **70.5 s**（n=128），最长间隔 **3.98 天**（11-09 晚 → 11-13 晚）。
- 按「间隔 <200 s 连成一场」分：16 场，大的几场是
  - 11-13 22:01（12 次）
  - **11-17 10:30–11:48（52 次）** —— 正好对上 `_folded` 那一段的 52 条崩溃行
  - 11-17 23:38（11 次）、11-18 00:08（14 次）、**11-18 08:06–08:24（12 次）**
- 每次停多久：129 次进程内重启的 stop→bind 中位 **4.2 s**（合计 921 s）；另有 39 次「>20 s」的 stop→bind 中位 **30.8 s**（合计 1337 s）。可测停摆合计约 **2258 s ≈ 38 分钟**（11-08→11-18）。
- `keeper.jsonl`：P2 被外部重启 **54 次**（11-15 14:22:24 → 11-18 10:29:48），间隔中位 **7.3 分钟**。

**限制**：bus.log 只有 181 条 stopping，比 235 条 bind 少 54 条（硬杀/重叠会话：53 次 bind 后面直接跟下一次 bind），所以 129 是**下限**；bus 的窗口和 P2.log 不重合，**129 不能和 153 相加**。单条崩溃的精确时刻、P2.log 的精确起止：**没查到**。

## 4. 每次崩掉什么、怎么恢复

### 恢复机制是三层

1. **进程内 supervisor**（`src/runtime/process_2_mind.py:583`）
   捕获 `BaseException` → 打 Traceback → 保存形状 → 退避 2/4/8/16 s（上限 60 s）→ 重跑 `main()`。
   同一个异常连续 5 次（`MAX_IDENTICAL_FAILURES=5`）→ 打印「放弃重启」并 `return 1`，进程退出。
2. **外部 keeper**（`tools/keeper.py`）
   每 5 s 看 `P2.heartbeat` 的 mtime；> `stale_s=30` 判死 → `python -m src.runtime.process_2_mind` 起新进程（cwd=仓库根，stdout **append** 到 P2.log，优先级 BelowNormal）。
   `min_life_s=15` 防止一拍一杀；连续 5 次「刚起就死」→ 自己也退出。
3. **启动 / 停止 / 单例**
   `tools/headless.py`、`scripts/start_all.ps1` 负责起；停止走 epoch 退休（control 通道），`scripts/stop_all.ps1` 则是 `taskkill /F /T` 硬杀。
   `src/common/epoch.py`：P1 领取 epoch（租约 15 s），P2/P3 采纳；`is_current()` 只比较 epoch 号 + retired。epoch 被换掉/被退休时，P2 当步就打印 `fenced, stopping` 主动退出（22 次），再等 keeper 拉起。

### 每次重启的恢复链

`Bus("P2")` 绑端口 → 读 `data/state/p2_runner.json`（surprise_hist/feature_hist）→ 等 epoch（≤15 s）→ 读 `data/state/l5.pkl` → `journal.replay()`（`data/journal/l5.wal`，append-only observations/recovers/folds）→ 订阅总线。

### 丢了什么（按证据）

1. **检查点**：168 个会话里 **101 次**收尾存档成功、**67 次失败**（全是质心超 1e6）。这 67 次重启只能回到**更早**的检查点，靠 journal 补。
2. **journal**：168 次重放；合计重放 observations **1748 条**，`available` 合计 2803。**111 次 `aborted=1`**：只要 WAL 里有一条坏记录，就整本作废、一条都不重放（journal.py:213「fail closed」）；其余次数里 `rejected` 合计 **929 条**（重放时逐条拒录非有限值，约 1/3）。
3. **runner 历史**：`runner state save failed: deque mutated during iteration` **299 次**（11-17/18 集中）。128 次重启里 127 次 `surprise_hist=256`、1 次 0（首次）——目前被「上限 256 很快补满」掩盖，但落盘失败本身是隐患（11-18 08:28 才在 persist 里先 `list()` 拷一份）。
4. **两套钟在分裂**：当前 `stream._step_count=384217`，`space._total_steps=386364`，**差 +2147 步**。journal 重放的 observations 只推进 space 的钟，stream 的 `_step_count` 不跟着走 → 每重启一次差一点。**这是「跨步累积状态」没有对账的直接证据。**
5. **停机期间的总线输入**：P1 的 surprise、L2 的 field 都是 pub/sub（latest），停着的时候不补发 → 重启后第一段没有外部输入。
6. **时间账失明**：`coma.json` 只由 P1 的 `begin_session()` 推进：`session_id=63`、`coma_events=8`、`uptime_s=898213`（≈249.5 h）、`coma_s=630617`（≈175.2 h）、`last_gap_s=15.3`、`rewound_s=100.9`。
   **P2 的 153 次「不在」一次都没记进昏迷账** → 她死着的时候 uptime 照常涨。
7. **会话内状态归零**：会话局部 `steps` / `transitions` / `last_snapshot` 每次重来；22 次 fenced 虽然走了正常路径，会话内状态同样归零。
8. **账本本身不可靠**：无时间戳、两种编码、152/153 Traceback、并发写坏一行；`start_all.ps1` 不重定向 stdout，而 keeper/headless 用 `ab` 追加——不同的启动方式写不同的账。这解释了为什么 P2.log 只留着 175 个会话，而 11-08 22:54 之后 bus.log 有 206 次 bind（差 31，**原因没查清**）。
