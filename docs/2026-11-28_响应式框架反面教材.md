# 响应式框架的反面教材（mofox src，2026-11-28 夜）

> 白默：**「shiromo 的框架层依旧是响应式聊天机器人，我当时创新的部分只有 cognitive core。
> 你要对响应式框架的 src 引以为戒。」**
> 这篇把 mofox/src 的模式列出来，作为 shiro_alice 的禁令清单。

## 一、mofox/src 的实际形状

| 证据 | 位置 | 含义 |
|---|---|---|
| `BaseChatter.execute(unreads: list[Message])` 是抽象入口 | `src/core/components/base/chatter.py:199` | **认知由“未读消息批次”触发** |
| `ChatterResult` 有 `Wait/WaitResumeEvent/Success/Failure/Stop` | 同文件 §34–93 | 对话是“一次执行→一个结果”的响应式状态机 |
| Chatter 管理器按 `stream_id` 过滤、维护 active instances | `src/core/managers/chatter_manager.py` | **每个聊天流是一个上下文/自我边界** |
| Action 是“主动的响应”，由 LLM Tool Calling 调用 | `src/core/managers/action_manager.py` 文件头 | 行动是回复链的一部分 |
| Bot 启动 `MessageReceiver`/`SinkManager`/插件 | `src/app/runtime/bot.py` | 框架的主循环是“收消息→处理→发消息” |
| 事件总线覆盖生命周期/会话节点 | `docs/app/runtime.md` | 事件驱动、插件热插拔 |

## 二、这些模式为什么是反面教材

1. **外部消息是时钟**：没有消息就没有 `execute`；她的“想”不是连续的，是批次的。
2. **对话流是自我边界**：`stream_id` 决定上下文；跨流要靠额外的“全局”补丁。
3. **回复是目标**：`ChatterResult` 围绕“这次回什么”组织；思考被回复绑架。
4. **LLM 在认知回路里**：Tool Calling/提示词是决策的一部分；不是“只翻译”。
5. **插件替代状态**：认知核心作为插件挂在聊天框架上，框架不改，插件再多也接不上
   （shiromo 自己的《检验清单》已经证明：src 一行没动）。
6. **同步/等待语义**：`Wait`/`Stop` 是对话状态，不是生命状态。

## 三、shiro_alice 的禁令（从这些模式反推）

| 禁令 | 对应她已有的原则 |
|---|---|
| 不许把外部消息当触发时钟 | ARCHITECTURE §3：无全局节拍；消息只是感知输入 |
| 不许按聊天流分裂自我 | 单一全局状态；跨流不是多个人格 |
| 不许把“回复”当目标 | L6 只是表达边界；想不被“该说什么”绑架 |
| LLM 不许进认知回路 | 硬约束 #1：LLM 只翻译，不思考 |
| 不许把认知做成宿主框架上的插件 | 她的框架就是她；没有“宿主聊天框架” |
| 不许用 Wait/Success 这类对话状态机 | 生命状态不是对话状态 |

## 四、可以学的部分（不是模式，是教训）

- 插件化本身不是错，错在**框架层不改，插件层补**；
- 事件总线不是错，错在**事件成为认知的触发者**；
- 多流不是错，错在**把流当自我**；
- 真正的教训是：**如果宿主是响应式的，认知永远是客人。**
  shiro_alice 不能再当客人——她的运行时必须本身就是“持续的她”。

## 五、与两条路线的关系

- shiromo 的 cognitive_core 是“客人”，所以它再像脑，也要靠宿主喂消息；
- shiro_alice 的目标路线是“她自己是宿主”，所以不能复制 mofox 的运行时形状；
- 这也是为什么“把 shiromo 的脑区模块搬进 shiro_alice”是半吊子：
  搬进来的是器官，宿主还是错的。

## 六、边界

- 只读 mofox/src 与文档，没有改任何代码；
- 本清单是禁令，不是新架构；架构选择仍见 `2026-11-28_线性链问题.md`（A/B/C）。
