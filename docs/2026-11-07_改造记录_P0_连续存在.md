## 1. P0-1 时间锚 + 昏迷补偿

### 做了什么

- `coma.json` 成为唯一时间权威：`saved_at / last_boot_at / session_id / uptime_s / coma_s / coma_events / last_gap_s / steps_per_second`。
- `begin_session()` 只由 P1 调用（P1 是唯一相位源）。`mark_saved()` 谁都能调，只更新 `saved_at`，幂等。
- 落盘时间章放在 `snapshot_all()` 的 **`finally`** 里。

### 对评估文档 §5.3 的一处修正（读代码之后）

§5.3 原文写"L0 slow/mid 向 baseline 解析松弛"。**读了代码，这条是错的**：

`mid_v/mid_w`（`mid_eps=0.008`）和 `slow_v/slow_w`（`slow_eps=0.0008`）都是 FHN 振子，
跑的是极限环，**没有可松弛的基线**。硬写"松弛到 baseline"就是在给这个项目加它明确要躲的死量化。

所以只对**有明确零驱动平衡点**的量做松弛：

- `SlowAccumulator.P`：零驱动时它自己的 decay 项把它拉向 `median(_hist)`。用它自己的规则，不引入新常数。
- 四个振子群体的 `(v, w)`：**相位在停机期间不可知，不补算、不假装知道**。
  P1 启动本来就有 4000 步预热让它们重新落回极限环。

### 实测（把 `saved_at` 回拨 3600 s，模拟一次真实停机）

```
[P1] 时间账本：session=7 | uptime=0.09h | coma=1.05h/1次 | last_gap=3611.0s
[P1] 她昏迷了 1.00 小时（第 1 次，累计 1.05 小时）
[P1] 零驱动松弛：P 0.2819 -> 0.0714（目标 0.0714，等效 2256892 步，settled）
```

`data/logs/events.jsonl` 里的对应记录：

```json
{"event": "coma", "gap_s": 3611.027, "session_id": 7, "coma_s": 3797.016,
 "coma_events": 1, "p_before": 0.281942, "p_after": 0.071449,
 "p_target": 0.071449, "applied": true, "reason": "settled"}
```

- 阈值 900 s：`gap=98.3 s` 那次只进 `coma_s`、不计 `coma_events`（快启），实测行为一致。
- 等效步数 2,256,892 = 3611 s ÷ 1.60 ms/step。那次用的是常量（账本里还没有实测值）；
  之后 P1 每 60 s 记一次实测步率，实测值 `steps_per_second = 469.85`（≈2.13 ms/step），
  补偿已改为优先用这个数：`gap 38.8 s → 17,243 等效步 → P 0.4125 → 0.8527（目标 0.8527）`。

## 2. P0-3 崩溃兜底

四个进程的 `__main__` 都换成 `_supervised()`：异常 → 打印堆栈 → 退避 `2/4/8/…/60 s` → 重新 `main()`。
`main()` 内部原有 `finally` 会把形状存盘，所以重启后能接着走，并会经过一次 `begin_session()`。

### 实测（在 `save_l1` 还没修的阶段）

```
session=2 | last_gap=2.7s
session=3 | last_gap=4.8s
session=4 | last_gap=8.9s
```

四次崩溃重启，进程没有永久死亡，账本逐次递增。**修好 `save_l1` 之后这个循环消失。**

### 补：永久错误要快速失败，不能无限重启

上面那版 supervisor 对**永久性**错误（端口被占、配置错、缺文件）也会一直重启，
只是退避变长 —— 实测端口冲突时每轮都打一整段 traceback，对无人看守的长期运行来说这比停下更糟。

改成：同一个错误连续 `MAX_IDENTICAL_FAILURES = 5` 次 → 放弃重启并返回 1。

实测（先起一个 P1 占住 5561，再起第二个）：

```
[SUPERVISOR] 崩溃（同一错误第 1 次），2s 后重启
[SUPERVISOR] 崩溃（同一错误第 2 次），4s 后重启
[SUPERVISOR] 崩溃（同一错误第 3 次），8s 后重启
[SUPERVISOR] 崩溃（同一错误第 4 次），16s 后重启
[SUPERVISOR] 同一错误连续 5 次，放弃重启：ZMQError: Address in use (addr='tcp://*:5561')
EXITCODE=1
```

## 3. P0-2 出生深度不再随运行时长衰减

`_birth_depth()` 的访问率从 `1.0 / total_steps` 改成 `_population_visit_rate()`：
已有区域"每次访问间隔多少步"的中位数。与 `viability.py` 里 `_born_step` 的口径一致了
——那个 bug 当时只对齐了 `R` 那一半。

|---:|---:|---:|---:|
| 10,000 | 3.846e-02 | 3.846e-02 | 1.0e-03 |
| 50,000 | 7.937e-03 | 3.846e-02 | 1.0e-03 |
| 147,664 | 2.702e-03 | 3.654e-02 | 1.0e-03 |

## 4. 顺手抓到一个既有 P0（原版 shiro 同样存在）

**现象**：P1 一启动就在第一次落盘崩溃：

```
AttributeError: 'L1Predictor' object has no attribute 'prev_z'
  persist.py:104  in save_l1   →  "prev_z": predictor.prev_z
  persist.py:339  in snapshot_all
  process_1_fast.py:1353 (主循环里的 persist 块)
```

**原因**：`L1Predictor` 重构时把 `prev_z` 改名为 `_prev_vec`（`process_1_fast.py:939/1069`），
`persist.save_l1` 没跟着改。

**后果**：`snapshot_all` 抛错 → `l0/l1/acc` 从那一刻起再也没被更新过，
`mark_saved` 也走不到（所以我第一版把时间章放在 try 里是错的，已改到 `finally`）。

**验证它不是我这轮引入的**：

```
git show d8f336f:src/runtime/process_1_fast.py | grep -c prev_z   →  0
```

即首次提交时 `process_1_fast.py` 里就已经没有 `prev_z` 了。

**修法**：`save_l1` 用 `getattr(predictor, "_prev_vec", None)`。
旧 checkpoint 里的 `prev_z` 会被 `load_l1` 的 `hasattr` 检查忽略，代价只是重启后第一帧少一段历史。

## 6. 这轮**没有**做的（有意留白）

1. **L5 / L3 的昏迷补偿**：需要"墙钟 → 等效 recover 次数"的换算。
   `steps_per_second` 已经开始记录（每 60 s 一次），但补偿本身还没写进 `terrain` / `trace`。
2. **L8 的 gap 节点**（§5.5）：昏迷必须被记住。这是"真实感"最关键的落点，需要单独设计。
3. **§6 第 5~9 条**：`_apply_scale_floor` 后 `_invalidate_centroids()`（会动性能，BRANCH.md 要求先测）、
   O(n²) 的 merge/scale、幽灵区域删除判据、不变量 pytest、20 行 `SpeechGate`。
4. **"昏迷 ≠ 睡眠"这条口径尚未落到 L7**：现在的实现只记账，不动睡眠压力/腺苷。
   这条需要白默确认——关机一周再开机，她该是"带着一周前的累"，还是"睡了一觉"。
