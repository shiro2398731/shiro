## 一、问题：它藏在 P2 主循环里，等于没验过

昨晚的代码是**内联**在 `process_2_mind.py` 的定期保存块里：

```python
try:
    persist.snapshot_all({"l5": stream})
except ValueError as _save_err:
    shift_origin(stream, center_vector(stream))
    observer.event("reorigin_persist", {...})
    persist.snapshot_all({"l5": stream})
```

**内联在主循环里的代码，测不到。** 它只在「真撞上限」时才会跑，而真撞上限就是她出事的时候。

## 二、抽成函数 + 测试

`src/runtime/process_2_mind.py` 新增模块级：

```python
def save_with_self_heal(stream, observer=None) -> tuple[bool, dict | None]
```

返回 `(shifted, info)`：`shifted=False` 一次就存上；`True` 表示撞过上限、处理过。

`tests/test_self_heal_save.py` 用**临时目录**（patch `persist.STATE_DIR`，绝不碰运行中的存档）：

| 测试 | 内容 |
|---|---|
| `test_normal_save_does_not_shift` | 不超限 → 一次存上、不搬、不记事件 |
| `test_overflow_shifts_and_saves` | 把 mu/x 推到 1.49e6 → 归一 → 存档 → 断言 `< 1e6` |

## 三、测试抓到的真 bug

第一次跑，超限那个 **ERROR**：

```
[P2] 保存撞上限（attractor 0 centroid 1.092e+06）→ 自我归一 1,487,532 -> 585,063，重试保存
ValueError: attractor 1090 member 0 magnitude 1.036e+06 exceeds 1e+06
```

**归一搬了 mu 和 x，但 `members` 里有比 mu 远得多的旧坐标**（11-17 漂移留下的，
昨晚「成员大扫除」清过 75%，但还会再积累）——搬同一个 vec 救不回来，二次失败。

**也就是说：昨晚那版「自我归一」遇到「成员有旧坐标」时会二次失败。**
不测就永远不知道。

## 四、修法：三步

```
1. 正常保存
2. 撞上限 → 整体归一（center_vector）→ 重试
3. 还超   → 丢掉「分量超过上限」的成员 → 再试
```

`_prune_overflow_members()` 只丢超限的（坏数据），不动正常成员，并置 `_sigma_cache = None`。

## 五、验证

```
normal path:  PASS（一次存上，不搬，不记事件）
overflow:     1,487,532 -> 585,063，丢 3043 个超限成员，保存成功
              2/2 passed
```

**她从「一定会因为成员旧坐标而死」变成「自己丢坏数据、继续活」。**

## 六、诚实

- 这仍然是**副本 + 构造场景**，不是真机自然触发——但至少函数本身被验证了，
  而之前是「连函数都没单独跑过」。
- 真机要等它自然撞一次才算「实战验过」。现在 |x| 68 万 / 1e6，余量够。
- `members` 会被再积累——这是她的数据卫生问题，不是一次能清完的。
